# Candidate card OPS-D — Exclusivity-marker soundness

- **Candidate name:** OPS-D — Exclusivity-marker soundness (stale-lock reclaim / ownership provability)
- **Plain-language invariant:** An operational exclusivity/ownership marker (a run lock, lease, or ownership record) must never be reclaimed, honored, or acted upon as authoritative solely on the basis of an identifier whose liveness or ownership cannot be proven within the current execution context. Marker validity must be structurally observable by the authority that grants it.
- **Exact semantic distinction:** marker validity is a property of the granting mechanism (a kernel handle dies with the process; a DB session lock dies with the connection; a lease expires on a clock) — provably tied to the owner's continued existence. It is not an inference from a reusable or context-ambiguous identifier (PID, hostname, filename) that the validating context merely interprets. Both failure directions are covered: falsely honoring a dead owner's marker (starvation) and falsely declaring a live owner dead (double execution / wrong-process action).
- **Trigger/applicability:** any Clank using operational exclusivity markers (run locks, leases, ownership records) to coordinate collection or writer execution across process or context boundaries. A Clank with no exclusivity markers at all is out of scope. All nine fleet members coordinate writers in some form.
- **Strongest evidence:** three independent environment discoveries of the identical unsoundness — oem-radar INC-009 (crash left `{"pid": 1}`; ~81 hourly fires refused to start: every container is PID 1 to itself), watch-clank INC-006 (inverse direction: a Windows `os.kill` liveness check could kill an unrelated process that reused the recorded PID), smartwatch-clank (PID/hostname reclaim proven broken in one-shot `docker run --rm`); plus smartphone INC-015 (stale PID file → duplicate daemons against one production DB) in the same identifier-liveness family. Remediation converged fleet-wide on OS-level advisory locks (`flock`/`msvcrt.locking`) that consult no PID at all.
- **Strongest counterexample:** "OS-level advisory locks are themselves mechanism prescription — a pure single-process Clank needs no lock, and a DB-session advisory lock looks nothing like `flock`."
- **Implementation freedom:** the locking mechanism (kernel advisory lock, DB session-scoped lock, lease service, or equivalent), marker storage, expiry policy, and reclamation UX are all free. The invariant constrains marker *validity semantics* only: liveness/ownership must be structurally observable by the granting authority, never inferred from a reusable identifier. All the mechanisms named above conform.
- **Fleet-Law relationship:** COMPLEMENT to ACTIVE Fleet Law 7 (writer coordination owns the principle that writers coordinate) and Fleet Law 5 (single scheduler authority owns "don't create competing authorities"); OPS-D binds the soundness of the coordination primitive itself — neither law addresses marker-validation semantics. No conflict; no restatement.
- **Why it deserves a distinct standard:** different invariant from OPS-A (a Clank deadlocked on a stale lock can record skip-outcomes perfectly and satisfy OPS-A's materialization contract while starving); different layer from Laws 5/7 (authority/coordination governance, not primitive soundness); four independent environment-dependent incidents across four repos with an escalating availability/correctness profile.
- **Evidence strength:** STRONG (four independent environment-dependent incident instances across four repos; remedy proven fleet-wide). **Fleet impact:** HIGH (81-run starvation observed; wrong-process kill observed). **Standardization risk:** LOW-MED (mechanism converged; scope must stay at validity semantics).
- **Recommendation: ADVANCE AS OPS-D** (candidate card advanced; STD-OPS-COM-004 drafting is deferred to a separately commissioned pass per the Pass 1.5 handoff).

## Counterexample test

**Strongest plausible counterexample:** "Database advisory locks, lease services, and distributed lock managers are legitimate and look nothing like `flock` — a standard naming OS advisory locks would outlaw them or mandate lockfiles."

**Does the candidate still hold?** YES, narrowed and clarified: the invariant constrains *validity semantics*, not mechanism. A DB-session advisory lock conforms — the DB server structurally observes the owner's death and reclaims it. A lease with expiry conforms — time-based reclamation is provable by the grantor. What fails the invariant is reclamation or honoring based on an identifier (PID, hostname) whose liveness/ownership the validating context cannot prove — the exact defect all four incidents share. Survives.
